# RPiKit

A modular, cross-platform Swift library for Raspberry Pi hardware peripherals, displays, graphics, and typography.

## Modules

- **`RPiHAL`**: Zero-dependency Hardware Abstraction Layer protocols (`GPIOPin`, `I2CBus`, `SPIBus`) and in-memory test mocks (`MockGPIOPin`, `MockI2CBus`, `MockSPIBus`).
- **`RPiLinux`**: Concrete Linux drivers leveraging `PeripheryKit` and Linux `spidev` ioctl. Stubs on macOS for seamless development.
- **`RPiGraphics`**: High-performance monochrome graphics engine, geometric types (`Point`, `Size`, `Rect`, `PixelColor`), frame buffers, and universal typography renderer with word-wrapping, multi-line support, and alignments (`.left`, `.center`, `.right`).
- **`RPiDisplays`**: Unified display drivers conforming to `MonochromeDisplay`:
  - `SSD1306` (128x64 I2C OLED)
  - `SSD1681` (200x200 SPI Waveshare 1.54" E-Paper)
  - `VirtualDisplay` (In-memory ASCII terminal display for local preview/unit testing)
  - `CoalescedRenderer` (Actor for coalescing rapid state updates during slow e-paper refreshes)
- **`RPiPeripherals`**: High-level hardware components such as `DebouncedButton` with `AsyncStream` event delivery.

## Installation

Add `RPiKit` to your `Package.swift` dependencies. Since `RPiKit` depends on `PeripheryKit` (which is tracked via branch), `RPiKit` does not currently provide version tags and must be installed using the branch variant:

```swift
dependencies: [
    .package(url: "https://github.com/Swift-Ahmedabad/RPiKit.git", branch: "main"),
]
```

Then add `RPiKit` to your target dependencies:

```swift
.target(
    name: "YourTarget",
    dependencies: [
        .product(name: "RPiKit", package: "RPiKit"),
    ]
)
```

> **Note**: You can also depend on individual modules (`RPiHAL`, `RPiGraphics`, `RPiDisplays`, `RPiPeripherals`, `RPiLinux`) if you do not need the entire umbrella library.

## Basic Standalone Usage

```swift
import RPiKit

// Initialize OLED (auto-uses /dev/i2c-1 on Linux, Mock on macOS)
let oled = SSD1306()
try oled.initialize()
oled.clear()
oled.drawString("Hello RPi", atX: 0, y: 0, font: .titleMedium20)
oled.drawHorizontalLine(y: 26)
oled.drawString("READY", atX: 0, y: 28, font: .label9, alignment: .right)
try oled.display()

// Monitor Hardware Button
let button = DebouncedButton(chipPath: "/dev/gpiochip0", pinNumber: 27)
for await event in button.events() {
    switch event {
    case .pressed:
        print("Button Pressed!")
    case .released:
        print("Button Released!")
    }
}
```

## Using RPiKit with Hummingbird & Swift Service Lifecycle

When building embedded web servers, REST APIs, or IoT microservices on a Raspberry Pi, hardware monitoring (push buttons, sensors, scheduled display updates) must run concurrently alongside the HTTP server.

Rather than spawning unmanaged background tasks (`Task.detached`) that leak hardware file descriptors and block clean shutdowns, you can integrate `RPiKit` directly into **[Hummingbird 2](https://hummingbird.codes)** and **[Swift Service Lifecycle](https://github.com/swift-server/swift-service-lifecycle)** (`swift-service-lifecycle 2`).

### Architectural Overview

                           |       (try await app.runService())   |

                                              |
                   +--------------------------+--------------------------+
                   |                                                     |
       +-----------v-----------+                             +-----------v-----------+
       |   Hummingbird Server  |                             |   HardwareService     |
       |     (NIO Engine)      |                             |   (ServiceLifecycle)  |
       |  Port 8080 REST API   |                             +-----------+-----------+
       +-----------+-----------+                                         |
                   |                                        withDiscardingTaskGroup
                   |                                                     |
                   |               +-------------------------------------+-------------------------------------+
                   |               |                                     |                                     |
                   |   +-----------v-----------+             +-----------v-----------+             +-----------v-----------+

                   |   | DebouncedButton.events|             |     Clock / Ticker    |             |      ADC / SPI        |

### 1. Thread Safety with Swift Actors

Incoming HTTP requests handled by Hummingbird execute concurrently on Swift NIO event-loop threads, while hardware interrupt and debounce loops run on background cooperative threads. To prevent data races, encapsulate all mutable hardware states and display rendering logic inside Swift `actor`s:

```swift
import Foundation
import RPiKit

actor HardwareManager {
    private let oled = SSD1306()
    private var pressCount: Int = 0
    private var isPressed: Bool = false

    func registerButtonPress(isPressed: Bool) {
        if !self.isPressed && isPressed {
            self.pressCount += 1
        }
        self.isPressed = isPressed
        renderOLED()
    }

    func currentStatus() -> (pressCount: Int, isPressed: Bool) {
        (pressCount, isPressed)
    }

    func renderCustomMessage(_ message: String) {
        do {
            try oled.initialize()
            oled.clear()
            oled.drawString("Server Notice", atX: 0, y: 0, font: .titleMedium20)
            oled.drawHorizontalLine(y: 24)
            oled.drawString(message, atX: 0, y: 32, font: .bodyMedium16)
            try oled.display()
        } catch {
            print("Failed to render OLED: \(error)")
        }
    }

    private func renderOLED() {
        do {
            try oled.initialize()
            oled.clear()
            oled.drawString("RPi Hummingbird", atX: 0, y: 0, font: .titleMedium20)
            oled.drawHorizontalLine(y: 24)
            oled.drawString("PRESS COUNT: \(pressCount)", atX: 0, y: 30, font: .label11)
            oled.drawString(isPressed ? "PRESSED" : "RELEASED", atX: 0, y: 46, font: .bodyMedium16)
            try oled.display()
        } catch {
            print("OLED render error: \(error)")
        }
    }
}
```

### 2. Implementing a Background `Service`

Create a service conforming to `ServiceLifecycle.Service`. Use `cancelWhenGracefulShutdown` and structured task groups (`withDiscardingTaskGroup`) to manage long-running hardware monitoring loops:

```swift
import Foundation
import ServiceLifecycle
import RPiKit

struct HardwareMonitoringService: Service {
    let hardwareManager: HardwareManager

    func run() async throws {
        // ServiceLifecycle triggers graceful shutdown without immediately cancelling the
        // service task. cancelWhenGracefulShutdown converts SIGTERM/SIGINT into task cancellation.
        await cancelWhenGracefulShutdown {
            await withDiscardingTaskGroup { group in
                group.addTask { await monitorButton() }
                group.addTask { await runPeriodicClock() }
            }
        }
        print("HardwareMonitoringService: Gracefully stopped.")
    }

    private func monitorButton() async {
        let button = DebouncedButton(pinNumber: 27)

        print("Listening for button events on GPIO 27...")
        for await event in button.events() {
            // Cooperative cancellation check
            guard !Task.isCancelled else { break }

            let isPressed = (event == .pressed)
            await hardwareManager.registerButtonPress(isPressed: isPressed)
        }
        print("Button listener exited.")
    }

    private func runPeriodicClock() async {
        while !Task.isCancelled {
            try? await Task.sleep(nanoseconds: 1_000_000_000)
            guard !Task.isCancelled else { break }
            // Perform periodic display refreshes or sensor readings...
        }
    }
}
```

#### Why Cooperative Cancellation Matters:
- `DebouncedButton.events()` yields an `AsyncStream`. Checking `guard !Task.isCancelled else { break }` ensures the loop terminates as soon as the service lifecycle signals shutdown.
- When the task group collapses, active hardware resources (such as `/dev/gpiochip0` lines or I2C/SPI file descriptors) are released immediately, preventing "device or resource busy" errors when the application restarts.

### 3. Registering Services with Hummingbird 2

In Hummingbird 2, the `Application` initializer accepts child services conforming to `ServiceLifecycle.Service`. Calling `try await app.runService()` boots both the HTTP server and all attached hardware services under a shared `ServiceGroup`:

```swift
import Hummingbird
import ServiceLifecycle

@main
struct ServerApp {
    static func main() async throws {
        let hardware = HardwareManager()
        let router = Router()

        // Expose HTTP endpoints that query or mutate hardware state
        router.get("/status") { _, _ -> [String: String] in
            let status = await hardware.currentStatus()
            return [
                "press_count": "\(status.pressCount)",
                "button_pressed": "\(status.isPressed)"
            ]
        }

        router.post("/message") { request, context -> [String: String] in
            struct MessageRequest: Decodable {
                let message: String
            }
            let body = try await request.decode(as: MessageRequest.self, context: context)
            await hardware.renderCustomMessage(body.message)
            return ["status": "ok", "delivered": body.message]
        }

        // Register the background hardware service
        let app = Application(
            router: router,
            configuration: .init(address: .hostname("0.0.0.0", port: 8080)),
            services: [
                HardwareMonitoringService(hardwareManager: hardware)
            ]
        )

        // Runs HTTP server + hardware services concurrently and handles SIGTERM/SIGINT
        try await app.runService()
    }
}
```

### 4. Handling Slow Peripherals (E-Paper) via `CoalescedRenderer`

E-Paper displays (such as `SSD1681`) require 1 to 3 seconds for a full refresh cycle over SPI. If multiple button clicks or HTTP requests arrive in rapid succession, refreshing synchronously will block the event loop and degrade API response times.

Use `CoalescedRenderer` from `RPiDisplays` to queue and coalesce rendering requests:

```swift
import RPiKit
import RPiDisplays

actor EPaperDisplayController {
    private let display = SSD1681()
    private lazy var renderer = CoalescedRenderer(display: display)

    func update(text: String, count: Int) {
        // Enqueues render; if an update is already in flight, newer state replaces the pending frame
        renderer.render { canvas in
            canvas.clear()
            canvas.drawString("System Status", atX: 0, y: 0, font: .titleMedium20)
            canvas.drawString("Count: \(count)", atX: 0, y: 40, font: .bodyMedium16)
            canvas.drawString(text, atX: 0, y: 70, font: .label11)
        }
    }
}
```

## Container & Process Lifecycle (Docker / systemd)

When deploying your Hummingbird + RPiKit application inside Docker on Raspberry Pi, the service must shut down cleanly on container stops (`docker stop` sends `SIGTERM`).

### Docker Device Permissions

Hardware pass-through in `docker-compose.yml`:

| Device Node | Hardware Bus / Function | Notes |
| :--- | :--- | :--- |
| `/dev/gpiochip0` | Character Device GPIO (cdev v2) | Used by `DebouncedButton` and hardware control lines |
| `/dev/i2c-1` | I2C Bus 1 | Used by `SSD1306` OLED |
| `/dev/spidev0.0` | SPI Bus 0 Chip Select 0 | Used by `SSD1681` E-Paper panel |

```yaml
services:
    rpi-service:
        image: rpi-server:latest
        restart: unless-stopped
        ports:
            - "8080:8080"
        devices:
            - "/dev/gpiochip0:/dev/gpiochip0"
            - "/dev/spidev0.0:/dev/spidev0.0"
            - "/dev/i2c-1:/dev/i2c-1"
```

> **Real-time Logging in Docker**: When running Swift binaries inside containers, line-buffering can delay log output. Prefix your executable command with `stdbuf -oL /app/ServerApp` in your `Dockerfile` or compose file so lifecycle and button logs display instantly in `docker compose logs -f`.
